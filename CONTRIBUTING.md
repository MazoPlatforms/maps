# Maintain Mazo Maps with individual JSON records

Contributors propose changes; administrators review and merge them on GitHub.
Accepted JSON files are the editable source of truth for the community layer.
GitHub authentication provides identities. There is no separate password store,
server-side mutation API, or frontend repository token.

## On the map

1. Click **＋ Contribute map data**. Choose **New record**, or select a published
   community record (including tombstones). Clicking a community point also opens
   a **Propose an edit** action. Search includes published community names/aliases.
2. Enter real public data, source attribution, observation date and an appropriate
   license. Never copy Google Maps or other proprietary map content. Do not publish
   private personal details. Check the underlying map for duplicate features.
3. Use map center for points, Draw/Finish for points, lines and simple polygons,
   or enter GeoJSON geometry. Coordinates are `[longitude, latitude]`.
4. Explain the change, confirm publication rights and prepare the JSON proposal.
   Review the before/after JSON. Download is local only and does not submit data.
5. New records: **Open GitHub proposal** prefills a new file. Contributors use a
   fork/new branch and open a pull request. Updating a record: download the JSON,
   open its exact path on GitHub, use **Edit file**, replace its contents and open a
   PR. Large proposals use GitHub's file upload or Git. Do not commit directly to
   main. GitHub may require sign-in or creation of a fork.
6. An administrator verifies the evidence, geometry, license and duplicates,
   reviews the JSON diff and PR GeoJSON artifact, then approves the exact commit.
   After merge, Pages builds/publishes the community layer. Deployment must succeed
   before the public map changes; a merge alone is not publication evidence.

Draft Save/Restore/Discard uses this device's localStorage. Drafts never publish
by themselves. Restoring a draft against a changed published parent is rejected.
The language fields preserve Tamil/Sinhala text; glyph/shaping availability still
belongs to the existing basemap renderer and is not recertified by this change.

## Source layout and lifecycle

`records/<featureType>/<first-two-ID-characters>/<UUID-v4>.json`.
The UUID and feature type never change. A move changes geometry, not the path.
Use `schemas/record-v1.json` for editor schema support. The shared
`assets/js/record-model.js` performs additional topology/size/transition checks.

New records start at revision 1 with `previous: null`. Each PR changes a record
once relative to the current base: increment its revision by one and set
`previous` to the SHA-256 of sorted-key, compact JSON plus one LF for the parent
record. Existing source entries must remain an unchanged prefix; append evidence.
Use the browser editor to calculate parent hashes. If another PR merges first,
reload/rebase your proposal onto the new parent. Resolve conflicts explicitly.

Deletion sets `status: "deleted"` and preserves the JSON, geometry, sources and
ID. Deleted features are omitted from map/search but available for admin inspection
and a reviewed restore. Git stores the complete source history. Admins roll back
through a new reviewed revision, not a force push or physical file removal.

Supported v1 geometry: place/infrastructure Point, road LineString, and building,
land, land_use, water, administrative_boundary simple Polygon with one closed
exterior ring. Maximum 500 coordinates, 128 KiB per record, 8 sources per record.
The bbox is not a legal national boundary or service-area determination. Boundaries
require authoritative evidence; this layer never changes the classifier or routing
network automatically. Roads here are visual features, not OSRM graph updates.

## Validate and preview locally

Node.js 22 or later; no npm installation is required for the production application.

```sh
node scripts/records.mjs --output data/community
node --test tests/*.test.mjs
python3 -m http.server 8000
```

Open `http://localhost:8000/`. As before, regional archives are generated by Actions,
so a plain local checkout does not include the national basemap. Browser verification
scripts provide isolated map fixtures or published archives; they do not seed
production records. To validate against a checkout of main and generate review data:

```sh
node scripts/records.mjs --base /path/to/main-checkout --report record-review --output data/community
```

`record-review/changes.json`, `before.geojson` and `after.geojson` are downloadable
PR artifacts. They are public proposal evidence; do not include secrets.

## Admin permissions and branch rules

Admins are GitHub logins in `.github/record-maintainers.json`; CODEOWNERS routes
reviews. The **Community admin approval** status uses trusted main code, GitHub
reviews and current-head SHA matching. A new push invalidates old approvals.
Non-author admins approve through GitHub Review. Explicit single-maintainer mode:
a maintainer author can post `/approve-records <full-current-head-sha>` on their own
PR after reviewing it. This is visible self-approval, not an independent review.
Outstanding current-head requests for changes prevent that status from passing.

Repository owners must enable main branch rules: require a pull request, require
`Community admin approval`, `records` (Validate JSON records), and `test` (Pages)
checks, dismiss stale reviews, require code-owner review where multiple maintainers
are available, and restrict bypass/direct pushes (including admins as appropriate).
Without those repository rules, CODEOWNERS and CI statuses are advisory; this patch
does not claim to have configured server-side enforcement. Lock down workflow,
schema, validator and maintainer changes with the same rules. Fork PR validation
has no write credentials; the review-status workflow never checks out/runs PR code.
The very first bootstrap PR uses the candidate validator because main does not yet
contain it; review that implementation before merging. Subsequent PRs use base code.

## Publication and data ownership

Individual records are compiled into two content-addressed static bundles: records
(including tombstones and sources) and active GeoJSON. The browser checksum-verifies
records and creates a MapLibre GeoJSON source. It never fetches every source file.
Git source records are not copied into the Pages payload. Generated files under
`data/community/` must not be edited or committed. Light/dark changes reinstall the
community layer. A Community records layer switch is available. Source-specific
licenses and attribution remain in the downloadable records. Review compatibility
of mixed-source data before accepting it; MIT covers software, not geographic data.

This bounded release permits up to 5,000 community records and 8 MiB per generated
bundle. It is not a plan to create millions of building files in the application
repository. Larger releases require partitioned indexes/tiles and separate storage.
The national Overture PMTiles remain an upstream baseline. Existing canonical
Colombo sample files/history are preserved and are not silently converted or
republished. Replacing/deleting an existing Overture feature is intentionally not
supported until a source-ID-preserving basemap, original-source verification,
release-conflict detection and suppression checks are integrated. Adding a duplicate
community feature is not an acceptable substitute for that work.

No production records are invented to demonstrate this flow. Acceptance still
requires a real contributor proposal, human evidence/license approval, successful
merge/deployment, and observation of that accepted feature on the public map.
